[도서 리뷰] 문제 해결을 위한 AI 에이전트 설계

알림

한빛미디어 서평단 <나는리뷰어다> 활동을 위해 도서를 협찬받아 작성된 서평입니다.

이번에 선택한 책은 문제 해결을 위한 AI 에이전트 설계 입니다. 요즘은 AI를 거의 매일 쓰다 보니, 필요할 때만 꺼내 쓰는 도구라기보다 늘 옆에서 같이 일하는 동료처럼 느껴집니다.
그런데 정작 “에이전트를 어떻게 설계해야 하는가"는 제대로 정리해 본 적이 없어서 이 책을 골랐습니다.

한마디로 에이전트를 만드는 법보다, 에이전트가 정말 필요한지부터 따져 보게 만드는 책입니다. 예제는 Python과 OpenAI API로 프레임워크 없이 직접 구현하는 방식이라, 프레임워크부터 써 보다가 안쪽이 어떻게 돌아가는지 궁금해진 분께 잘 맞을 것 같아요.

AI를 어디에 써야 할까?#

저자는 소프트웨어 1.0, 2.0, 3.0이라는 세 가지 패러다임을 기준으로, 문제를 먼저 나눠 보고 거기에 맞는 방식을 골라야 한다고 이야기합니다. 기준은 두 가지입니다. 입력과 출력이 정형인지 비정형인지, 그리고 답이 하나로 정해지는 결정론적 문제인지 아닌지입니다.

  • 소프트웨어 1.0: 사람이 규칙을 직접 코딩합니다. 정형 + 결정론적 문제(제1사분면)에 맞습니다.
  • 소프트웨어 2.0: 데이터로 모델을 학습시켜 패턴을 인식합니다. 이미지 분류처럼 비정형이지만 답이 정해진 문제(제2사분면)에 맞습니다.
  • 소프트웨어 3.0: LLM에게 자연어로 일을 시킵니다. 답이 하나로 정해지지 않는 비결정론적 영역에서 힘을 발휘합니다.

LLM은 사람이 하는 말, 즉 자연어 질문을 그대로 이해합니다. 이제는 개발자가 들어올 패턴을 미리 다 예상해서 코딩할 필요가 없는 거죠. 그렇다고 모든 걸 LLM에게 맡기라는 이야기는 아닙니다. 규칙으로 충분한 부분은 코드로 처리하고, LLM은 꼭 필요한 곳에만 두라는 게 이 책의 핵심입니다.

이 부분을 읽으면서 뜨끔했습니다. 저도 요즘은 일단 AI한테 물어보고 시작하는 경우가 많은데, 사실 정규식 하나나 if문 몇 줄이면 끝날 일까지 LLM에게 맡기고 있었던 것 같네요..

에이전트는 결국 추론하고, 도구를 고른다#

에이전트의 기본 동작은 생각보다 단순합니다. 사용자가 날씨를 물어보면 LLM은 아래와 같은 흐름으로 추론합니다.

사용자: "오늘 날씨 어때?"
  -> LLM 추론 : 날씨 정보가 필요함 -> 날씨 API를 사용하자
  -> 날씨 API 호출 및 응답
  -> LLM 추론 : 날씨 정보를 받았으니 사용자에게 전달하자
  -> LLM 출력 : "오늘은 맑습니다."

기본적인 토대는 이 형태라고 보면 됩니다. 결국 얼마나 복잡하냐의 문제이지..
도구가 늘어나고, 이전 대화를 기억해야 하고, 여러 단계를 반복해야 하면 그만큼 복잡해집니다. 책에서도 도구, 메모리, 반복 실행은 필요한 만큼만 더하라고 강조합니다.

책은 이 흐름을 바탕으로 텍스트 어드벤처 게임, 영어 회화 연습 에이전트, 자동 리서치 에이전트 같은 예제를 하나씩 만들어 가고, 마지막 장에서는 코딩 에이전트까지 직접 조립합니다.

매일 쓰는 Claude Code 같은 도구도 큰 틀에서는 이 루프를 정교하게 다듬은 것이라고 생각되네요.

AI는 만능이 아니다#

AI도 결국 주어진 도구 안에서만 일할 수 있습니다. 예를 들어 오늘 주가를 물어봐도, 시세를 조회할 도구가 없으면 실시간 정보에는 접근할 수 없다고 답하거나 학습 시점의 오래된 정보로 답할 뿐입니다. 모델이 아무리 똑똑해도 손발이 없으면 할 수 있는 게 없는 거죠.

반대로 도구가 있다고 해서 늘 알아서 쓰는 것도 아닙니다. Claude Code에서 특정 제품의 중고 시세를 물어봤을 때, /effort가 낮으면 정보를 찾을 수 없다고 끝내 버리고, /effort를 높이니 그제야 웹 검색으로 직접 찾아보더라구요.
같은 모델이라도 도구를 쓸 수 있는지, 그리고 그 도구를 꺼내 쓸 만큼 깊게 생각하게 하는지에 따라 결과가 꽤 달라진다는 걸 체감했습니다.

요즘 MCP(Model Context Protocol)가 많이 이야기되는 것도 같은 맥락인 것 같습니다. MCP는 모델에 도구를 연결하는 방식을 표준으로 정하는 방식입니다.

만든 다음이 진짜 시작#

에이전트를 한 번 돌려 보는 것과 실제로 운영하는 건 완전히 다른 이야기입니다. 책의 중반 이후에서는 이런 실무적인 부분을 다룹니다.

  • 신뢰성 : 재시도, 타임아웃, 응답 형식 검증
  • 비용 : 토큰 관리와 캐싱
  • 보안 : 프롬프트 인젝션, 권한 관리, 샌드박스
  • 평가 : 최종 결과와 실행 과정을 나눠서 평가하고, 변경 전에 회귀 평가를 거치기
  • 컨텍스트와 메모리 : 무엇을 기억하고 무엇을 버릴지

회사에서 AI 도입 이야기를 할 때도 결국 “그래서 비용은 얼마나 들고, 보안은 괜찮아?“라는 질문이 먼저 나옵니다. 데모를 잘 만드는 것보다 이 질문에 답할 수 있어야 실제로 쓸 수 있는 에이전트가 된다는 점에서 이 파트가 가장 실무에 와닿았습니다.

특히 평가 부분이 인상 깊었습니다. LLM은 같은 입력에도 매번 다른 답을 줄 수 있어서, 프롬프트를 조금 고쳤을 때 좋아진 건지 나빠진 건지 감으로만 판단하기 쉽습니다.
일반 코드에 테스트를 붙이듯이 에이전트에도 평가를 붙여야 한다는 이야기는 앞으로 꼭 챙겨야겠다고 생각했습니다.

느낀 점#

가장 좋았던 건 “어떻게 만들까"보다 “어디에 만들지 말아야 할까"를 먼저 생각하게 해 준다는 점입니다.
에이전트를 붙일지 말지 고민될 때 꺼내 볼 기준이 하나 생긴 느낌이에요. 프레임워크 없이 바닥부터 만들어 가는 방식이라, 에이전트가 안에서 어떻게 돌아가는지 이해하기도 좋았습니다.

다만 예제가 OpenAI API 기준이라 API 키를 발급받고 사용한 만큼 비용을 내야 한다는 점은 조금 아쉬웠습니다.
Claude나 Gemini를 주로 쓰는 분이라면 코드를 조금 바꿔서 따라 해야 할 것 같아요.

LLM API로 간단한 기능은 만들어 봤지만 에이전트는 어떻게 설계해야 할지 감이 안 오는 분, 그리고 팀에 AI 도입을 고민하고 있는 분께 추천합니다.

올해 AI 관련 책과 강의를 꽤 많이 봤는데, 대부분 특정 도구를 잘 쓰는 법에 가까웠습니다. 이 책은 도구가 바뀌어도 남는 문제를 나누고 역할을 정하는 감각을 다룬다는 점이 좋았습니다. AI 도구는 앞으로도 계속 바뀔 테니, 결국 이런 기본기가 더 오래 쓰이지 않을까 싶네요.
